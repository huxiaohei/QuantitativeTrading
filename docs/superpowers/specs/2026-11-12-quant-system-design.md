# 个人 A股 低频量化系统 · 设计文档（第一版）

日期：2026-11-12
状态：待用户确认

标注说明：**【用户】** 表示用户明确说过的内容；**【我的判断】** 表示设计者替用户做的选择，用户可以否决。未标注的数值均为默认参数，全部可配置，并应由回测结果来校准。

## 1. 意图

用户平时手动炒股，方法是：找股息率不错、价格处在最近一年低位的股票买入，赚 10~15% 卖出；买入后下跌则持有不动，有时最终割肉。【用户】

这套系统要把这个做法变成明确的程序规则，用历史数据检验它是否有效，每天自动扫描全市场，在买卖时机出现时通知用户，并补上用户现在缺少的部分：亏损时的退出规则和整体风险控制。

用户不熟悉量化交易，但有 10 年后端开发经验，希望能读懂并亲手修改代码里的规则。【用户】

## 2. 目标

1. **规则化**：把用户的选股和买卖做法写成可配置、可回测的策略。
2. **回测验证**：在十年左右的历史数据上检验策略，并与直接持有指数做比较。
3. **风险控制**：独立的风控层，所有信号必须先通过它。【用户：低买高卖的同时控制风险】
4. **邮件通知**：交易的不同阶段发对应邮件。【用户】
5. **从成败中学习**：记录每笔交易的理由和结果，定期生成复盘报告。【用户】
6. **可读可改**：代码结构清晰，策略是独立模块，用户可以自己加策略、改规则。【用户】
7. **顺带科普**：每个信号附带"为什么买 / 为什么卖"的说明，文档解释用到的概念。【用户】

## 3. 不做的事（第一版）

- 港股。【用户：先放一放】
- 自动下单。第一版是"系统出信号，用户在平安证券 App 手动下单"。【我的判断，用户已知悉】
- 多策略。框架留出接口，但只实现一个策略。【用户已同意】
- 日内或高频交易、分钟级数据。
- 机器学习、自动调参。
- 网页界面。交互通过命令行、配置文件、邮件和 HTML 报告完成。【我的判断】

## 4. 即使技术上跑通也算失败的情况

- **系统自动修改交易规则**。规则只能由用户看过复盘数据后亲手改。【我的判断，已向用户说明理由：容易把运气当规律】
- **回测结果虚高**：用到了未来数据、忽略交易成本、忽略涨跌停买卖不了的情况。免费数据确实拿不到的部分（见 6.1）不算失败，但必须在回测报告里明确披露，不能悄悄忽略。
- **信号没有解释**，用户不知道为什么买卖。
- **系统保存券商账号密码**，或在用户不知情时动用资金。
- **代码过度抽象**，用户读不懂、不敢改。

## 6. 系统组成

```
数据层 ──► 策略层 ──► 风控层 ──► 信号 ──► 邮件通知
  │          ▲                      │
  │          │                      ▼
  └──► 回测引擎              用户手动下单
                                    │
                                    ▼
                        成交录入 ──► 交易日志 ──► 复盘报告
```

回测和每日实盘运行使用**同一份策略代码和同一份风控代码**，区别只在数据来源和成交方式。这是核心结构要求，避免"回测一套、实盘一套"。

### 6.1 数据层

- 数据内容：全部 A股 的日线行情（含复权因子）、分红记录、主要财务指标、行业分类、交易日历、ST 状态、上市和退市日期、基准指数行情。
- 数据源：AKShare（免费）。数据源封装在一个接口后面，将来可以换成 Tushare 等。【我的判断】
- 存储：行情和财务数据用 Parquet 文件，通过 DuckDB 查询；持仓、信号、交易日志等状态数据用 SQLite。【我的判断】
- 每个交易日收盘后增量更新。更新失败或数据异常（例如某日数据缺失、价格跳变超出涨跌停范围）时停止后续流程并发告警邮件，不带着坏数据出信号。
- **时点正确性**：财务数据和分红数据必须按公告日期使用，回测中某一天只能看到当天之前已经公告的信息。
- **已知风险**：免费数据源对已退市股票、历史 ST 状态、财报和分红的真实公告日、历史行业分类的覆盖可能不完整，这会让回测结果偏乐观。用户已决定第一版接受这一点【用户】。构建者在阶段一开头先核实 AKShare 实际能拿到什么，拿不到的部分采用保守的近似处理（例如公告日缺失时按法定披露截止日使用财报），并在回测报告里逐项列出缺口和可能的偏差方向。数据源接口要保持可替换，方便以后接入付费数据后重跑回测对比。

### 6.2 策略层

策略是一个独立的类，输入是"截至某日的数据 + 当前持仓"，输出是"买入候选列表 + 卖出列表"，每一条都带有触发原因和当时的指标数值。新增策略等于新增一个类。

第一版策略：**高股息低位**。

**股票池过滤**
- 默认只包含沪深主板。科创板和北交所有 50 万资产门槛，用户资金量不满足，排除。创业板做成配置开关，默认关闭。【我的判断，用户已确认】
- 剔除 ST、上市不满 3 年、近 60 日日均成交额低于 5000 万的股票。
- 剔除一手金额超过单笔预算的股票。

**买入条件（全部满足）**
- 股息率（近 12 个月已公告分红 ÷ 现价）不低于 4%。【用户做法的规则化】
- 价格处于一年低位：`(收盘价 − 250日最低) ÷ (250日最高 − 250日最低) ≤ 0.2`。【用户做法的规则化】
- 质量过滤【我的判断，用于避开"价值陷阱"】：
  - 连续分红不少于 5 年
  - 近 3 年平均 ROE 不低于 8%
  - 分红占净利润比例不高于 80%
  - 最近一期净利润同比下滑不超过 20%
  - 资产负债率不高于 70%（银行、保险、券商不适用此项）
- 候选数量超过可买数量时，按股息率从高到低排序。

**卖出条件（任一触发）**
- 止盈，两种方式都实现，由回测比较后选定：
  - 固定止盈：盈利达到 12%。【用户现有做法，取其 10~15% 的中间值】
    - 2026-11-13 更新：默认值改为 20%。【用户】原因：12% 在 2015–2021 年年化 11.33%，但在 2022 年以后只有 3.13%，跑输红利 ETF；20% 在两段分别为 8.91% 和 11.04%，都高于同期红利 ETF。注意这次修改是在看过样本外结果之后做的，样本外数据已不能再用来验证它。
  - 移动止盈：盈利达到 10% 后启动，从持有期最高价回落 8% 卖出。【我的判断，作为对比项】
- 价格止损：亏损达到 15%。【我的判断】
- 时间止损：持有满 250 个交易日仍未盈利。【我的判断】
- 基本面止损：公司公告的分红低于上年，或最近一期净利润同比下滑超过 30%。【我的判断】

盈亏计算包含持有期间收到的分红。

### 6.3 风控层

独立于策略，策略给出的每个信号都要经过它，可以否决或缩小买入数量。【我的判断，数值已向用户说明】

- 单只股票不超过总资产的 10%，最多同时持有 10 只。
- 单一行业不超过总资产的 30%（高股息股票容易扎堆在银行、煤炭等行业）。
- 买入数量向下取整到 100 股；现金不足则不买。
- 账户总资产从历史最高点回落 15%：发预警邮件。
- 回落 20%：停止发出新的买入信号，卖出信号照常。
- 恢复规则：暂停满 60 个交易日后自动恢复买入，并把"历史最高点"重置为恢复当日的总资产，避免恢复后立刻再次触发。回测和实盘用同一条规则；实盘中恢复时发邮件，用户也可以用命令提前恢复或延长暂停。【我的判断，用户已确认】
- 回撤按份额法净值计算：用户追加或取出资金通过一条命令录入，不计入盈亏，也不会误触发回撤线。【我的判断】
- 冷却期：因价格止损、时间止损或基本面止损卖出的股票，60 个交易日内不再买入，避免止损后第二天又被选中。止盈卖出的不受此限。【我的判断，用户已确认；天数可配置，可用回测对比】
- 用户提到亏损 50% 是其心理上限【用户】。这不作为运行参数，而作为验收标准：若回测中最大回撤接近这个水平，策略需要重做。

### 6.4 回测引擎

- 自行编写一个简单的按日回测器，不使用现成回测框架。【我的判断：代码量不大，A股 特有规则更容易写对，用户也更容易读懂】
- 成交假设：T 日收盘后产生信号，T+1 日按开盘价成交；T+1 日开盘涨停则买不进，跌停则卖不出，顺延到下一日。
- 成本：佣金万分之 2.5、每笔最低 5 元（用户应改成自己的实际费率）；卖出印花税 0.05%；过户费 0.001%；滑点 0.1%。
- 回测区间：2015 年至今，覆盖 2015 年股灾、2018 年下跌、2020 年和 2022 年等不同行情。
- 防止过度调参：2015~2021 年的数据用于选参数，2022 年之后的数据只用于检验，不参与调参。
- 输出一份 HTML 报告：年化收益、最大回撤、夏普比率、胜率、盈亏比、平均持有天数、年换手率、净值曲线、各退出原因的次数和平均盈亏、逐笔交易清单。
- 比较基准：沪深300 全收益指数、红利 ETF（510880）。策略需要回答"比直接买指数强在哪里"。
- 提供参数敏感性对比命令，例如同时跑股息率门槛 3% / 4% / 5%，看结果是否对参数过于敏感。

### 6.5 每日运行流程

每个交易日 18:00 左右由 macOS 的 launchd 定时触发。【我的判断】

1. 更新数据并做完整性检查。
2. 检查现有持仓是否触发卖出条件。
3. 扫描全市场，找出买入候选。
4. 通过风控层，生成最终信号。
5. 发邮件。
6. 用户次日在平安证券 App 手动下单，之后用一条命令录入实际成交的价格和数量。系统以用户录入的实际成交为准来更新持仓。
7. 信号发出后 3 个交易日内没有录入成交则视为放弃，并在邮件中提醒一次。

电脑当时处于关机或休眠而错过运行时，下次开机后补跑。

### 6.6 邮件通知

通过 SMTP 发送，邮箱服务商可配置，授权码放在本地 `.env` 文件中，不进入代码库。

| 邮件 | 触发时机 |
|---|---|
| 买入信号 | 有新的买入候选通过风控。包含股票、建议股数、参考价、各项指标值、买入理由、预设的止损和止盈位置 |
| 卖出信号 | 持仓触发止盈、价格止损、时间止损或基本面止损，写明是哪一种 |
| 成交确认 | 用户录入成交后，回显最新持仓 |
| 风控预警 | 账户回撤达到 15% 或 20% |
| 周报 | 每周五：持仓盈亏、本周交易、账户净值与基准对比 |
| 月度复盘 | 见 6.7 |
| 系统异常 | 数据更新失败、程序报错 |

没有信号的日子不发邮件，以周报为准。【我的判断】

### 6.7 交易日志和复盘

这是"从成败中学习"的落地方式。【用户目标，实现方式是我的判断】

- 每笔交易记录：买入时的全部指标快照和理由、卖出原因、持有天数、盈亏、系统信号价与实际成交价的差距。
- 卖出之后继续跟踪该股票 20 日和 60 日的走势，用来回答"止损之后它涨回来了吗"、"止盈之后它是不是还在涨"。
- 被风控否决的信号、用户选择不执行的信号也记录下来，同样跟踪后续走势。
- 月度复盘报告：胜率、盈亏比、按退出原因分组的统计、实盘与同期回测的偏差、与基准的对比。
- 报告只呈现数据和观察，不自动改参数。用户看后自己改配置，并可以先用回测检验改动。

## 7. 技术选型【除标注外均为我的判断】

- 使用 Python【用户】，版本 3.12，用 uv 管理依赖
- 所有函数参数都带类型标注【用户】，返回值也一并标注【我的判断】
- 代码不能有任何告警【用户】。落实方式【我的判断】：ruff 检查和 pyright 严格模式均为零告警，pytest 把运行时告警当作错误处理；第三方库缺少类型信息时用类型桩或在边界处封装，不靠大面积忽略规则来达标
- pandas、DuckDB、SQLite、AKShare
- 命令行入口用 Typer
- 参数放在 YAML 配置文件里，策略逻辑放在 Python 代码里
- pytest 测试，重点覆盖风控规则、回测成交规则（T+1、涨跌停、一手取整、费用）和时点正确性
- 用 git 管理代码；数据文件、`.env`、SQLite 状态库不入库

## 8. 分阶段交付

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| 一 | 数据层 + 回测引擎 + 策略 | 用户拿到回测报告，据此确定参数和止盈方式 |
| 二 | 每日运行、风控、邮件、成交录入、交易日志 | 系统每天自动运行，以纸上模拟方式跟踪至少 1~2 个月，不投入真钱 |
| 三 | 小资金实盘 + 月度复盘 | 实盘结果与回测大体一致后再逐步加大资金 |
| 以后 | 更多策略、自动下单、港股 | 另行设计 |

阶段一结束时有一个决策点：如果回测显示这套策略扣除成本后并不优于红利 ETF，需要和用户一起决定是改规则还是换思路，而不是直接进入阶段二。
