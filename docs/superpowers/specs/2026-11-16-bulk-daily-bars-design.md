# 每晚日线改用批量行情：设计

日期：2026-11-16。状态：用户已确认（"可以，开始改"）。

## 为什么要改

每晚日线更新是逐只请求，3487 只股票各 2 次请求。数据源正常时约 2 小时 40 分钟；
2026-11-15 试运行那晚数据源响应差，用了 8.5 小时（见 `docs/deploy-mac.md` 的首次试运行记录）。
目标：数据源正常时整晚约 50 分钟，并把请求次数从约 7000 次降到约 1000 次。

## 实验依据（2026-11-16，只读）

- 东方财富批量行情 `stock_zh_a_spot_em`：这条线路被限流，直接报错，不用。
- 新浪批量行情 `stock_zh_a_spot`：18.5 秒取回 5578 只。与库里 2026-11-13 的 3185 根日线比较，
  开、高、低、收、成交量、成交额全部相同（现有逐只接口也是新浪）。
- 批量数据的"昨收"与库里 2026-11-12 收盘价不同的有 7 只，当天复权因子变化的也正好是这 7 只。
- 停牌股票在批量数据里开盘价、最新价、成交量都是 0。
- 批量数据没有日期列，只有时间戳（时分秒）。

## 做法

数据源协议新增 `daily_snapshot()`，返回列：`symbol`、`open`、`high`、`low`、`close`、
`prev_close`、`volume`、`amount`（代码去掉交易所前缀，只保留 6 位）。

`update_all` 的日线阶段（`update_all` 不读系统时钟，当前时间由调用方以 `now` 传入：每晚任务传注入的时钟，
`qt data update` 传真实的上海时间；不传则整晚逐只请求）：

1. **是否启用**（任何一条不满足，整晚用原来的逐只方式，原因记入运行报告）
   - 配置 `data.bulk_bars` 为真（默认真）。
   - `as_of` 等于最近一个已收盘的交易日，且当前时间在它收盘（16:00）之后、下一个交易日 09:00 之前；
     交易日历里没有下一个交易日时不启用。
   - 至少有一只要更新的股票，库里最后一根日线正好是 `as_of` 的前一个交易日（否则不请求批量接口）。
   - 批量接口调用成功（只尝试一次，失败不重试，避免加重限流）。
   - "可比对的股票"＝库里最后一根日线正好是前一个交易日、且批量数据里有它的股票。其中**没有成交**
     （成交量不大于 0）的比例不超过 10%（`SNAPSHOT_MAX_NO_TRADE`）；超过说明批量数据被部分清零或不完整。
   - 可比对且有成交的股票不少于本次要更新、还没有 `as_of` 日线的在市股票的 50%（`SNAPSHOT_MIN_COVERAGE`），
     否则比例闸门样本太小（包括开盘前全部清零、可比对且有成交的为 0 只的情形）。
   - 可比对且有成交的股票中，`prev_close` 与库里该日收盘价相差不超过 0.005 的比例不低于 90%
     （`SNAPSHOT_MIN_MATCH`）。比例不够说明批量数据不是 `as_of` 那天的。
2. **逐只判断**。一只股票用批量数据要同时满足：
   - 库里最后一根日线正好是 `as_of` 的前一个交易日；
   - 批量数据里有它（代码重复出现的整行丢弃），且 `open > 0`、`close > 0`、`volume > 0`，
     最高价、最低价、成交额都是有限数；
   - `prev_close` 与库里前一日收盘价相差不超过 0.005；
   - 库里分红表没有它在 `as_of` 除权除息的记录（分红很小、参考价没变的情形）；
   - 库里前一根日线的 `adj_factor` 是大于 0 的有限数。

   满足：写入 `as_of` 的日线，`adj_factor` 沿用库里前一根日线的值（不重新计算）。
3. **停牌**：批量数据里这一行成交量、开盘价、最新价都是 0，昨收与库里前一日收盘价相差不超过 0.005，
   且库里最后一根日线正好是前一个交易日——不写日线，也不逐只请求，不记失败，计入"判为停牌"只数。
   成交量为 0 但价格不为 0、或昨收对不上的，不算停牌，走逐只请求。
   （如果它落后超过一天，仍走逐只方式把中间缺的日子补上。）
4. **其余全部走原来的逐只请求**：当天除权（昨收对不上）、落后超过一天、从未下载过、
   批量数据里没有这只股票等。逐只请求的失败处理、进度输出不变。
5. **熔断**：只有本只股票有请求成功返回时才把"连续网络失败"清零；没有联网的股票（批量写入、停牌、
   已是最新且基本面没到期）不改变连续失败数，所以批量的晚上连续多只网络失败仍会中止运行。

财务与分红的滚动刷新不变。补跑多天时，较早的日子不满足第 1 条，自然用逐只方式。

## 不做

- 不处理财务与分红那约 47 分钟。
- 不改回测、策略、两本账的任何逻辑。日线表结构不变。

## 失败情形

- 批量数据被部分清零（一部分股票显示无成交）→ 第 1 条的无成交比例闸门拦住；单只"成交量 0 但价格不为 0"
  或"全 0 但昨收对不上"走逐只请求。

- 批量数据其实是别的日子的 → 第 1 条的比例闸门拦住。
- 当天除权但昨收恰好与前收相同（分红极小、参考价没变）→ 库里分红表已有这条除权记录时走逐只请求；
  记录还没入库时会沿用旧的复权因子，误差至多万分之几，核对命令可事后发现。
- 批量接口报错或被限流 → 退回逐只方式，不比现在差。
- 批量数据缺某只股票 → 该股票走逐只方式。

## 验收

- 测试覆盖上面每个分支，包括各道整体闸门。
- 新增只读命令 `qt data check-snapshot [--sample N]`：取一次批量数据，对抽样股票（有成交的 N 只，
  另加批量数据显示停牌的至多 5 只）用逐只接口取同一天的日线，报告两者是否逐项相同、复权因子是否与沿用值一致；
  显示停牌的股票逐只接口不应有当天日线。每只股票恰好计入一类（一致、不一致、当天除权、无法核对）。
  不写任何数据；有不一致或无法核对时退出码为 1。
- 运行报告和 `daily_runs.detail["bulk"]` 里记录：是否启用批量（used）、批量写入多少只（bars）、
  判为停牌多少只（suspended）、逐只请求多少只（per_symbol）、未启用的原因（reason）；`qt admin runs` 每天打印一行。
- 对真实数据跑一晚：记录耗时；用核对命令确认一致。
